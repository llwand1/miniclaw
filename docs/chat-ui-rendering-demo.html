1

回复效果 ≠ 动画，而是一套「渲染层契约」核心心智

WorkBuddy / OpenCode 那种"会思考、会调工具、流式排版漂亮"的回复，不是前端堆动画堆出来的。真正的核心是：前后端约定一份事件形状契约——后端把 LLM 原始流切成结构化事件，前端按事件类型渲染对应组件。点下面按钮，看数据是怎么流动的。

点「播放数据流动」，看 LLM → Gateway → Frontend 的链路 ↑
关键认知：我们之前那版只做了"token 流 + 前端猜阶段"，所以显得"哑"。真正的差距是中间这层结构化事件契约和真正的 Markdown / 代码渲染——这正是 Section 2 要演示的。
为什么不能只靠 token 流，前端自己猜？
因为信息丢失。纯 token 流里，思考过程、工具名、工具参数、工具结果、产物元数据全混成一段文本，前端无法区分，只能硬猜（我们之前就是这么干的，所以阶段条是"猜"出来的）。结构化事件让每个语义单元有独立形状，前端才能分别渲染成思考块 / 工具卡片 / 代码高亮 / Artifact 预览，且能精确控制动画与状态。

可交互演示：理想回复长什么样最终产出原型

下面是一段模拟的完整 AI 回复。点「▶ 播放一次完整回复」，你会看到后端按顺序吐出结构化事件，前端实时渲染：阶段指示条 → 可折叠思考块 → 实时工具卡片 → 流式 Markdown（标题/列表/代码高亮/表格）+ 打字光标。这就是我们对标 WorkBuddy 的"最终产出"视觉。

回复界面那种效果，到底是怎么实现的？
思考过程
点「播放一次完整回复」，看事件如何驱动前端渲染 ↑
这就是"渲染层契约"的直观体现：前端是一个事件驱动的渲染器（reducer + effect）。每次收到一个事件，只更新对应区块（思考块 append、工具卡实时翻转、回答区 append token），绝不重渲整页。所以你能看到"思考中→调工具→写回答"平滑过渡，而不是一次性蹦出整段文字。
流式 Markdown 怎么做才不会"重播闪烁"？
两个要点：① 按行分块 + 稳定 key——把已输出的每一行用其在文本中的固定索引当 key，diff 时只渲染"新增的行"，已有行不复用重建，避免整段重新淡入；② 末尾 caret 单独放，不计入正文 diff。我们之前那版用"整段重渲 + 每行淡入"会有重播感，正式版要改成稳定 key 分块。
3

后端契约：六种结构化 SSE 事件SSE 形状

Gateway 不吐裸 token，而是吐这六种带形状的事件。前端只认事件 type，不关心具体 UI。下面每个事件是真实 payload 示例（即 MiniClaw 的 SSE-CONTRACT.md 要扩展的目标）。

token
正文增量，前端 append 到 Markdown 渲染区。
{ "type":"token", "content":"# 标题" }
reasoning
推理过程增量（DeepSeek-R1 / o-series 才有；非推理模型不返回，前端须容错）。
{ "type":"reasoning", "content":"用户在问…" }
tool_call
工具调用开始，带结构化 name + arguments（不是字符串）。
{ "type":"tool_call", "id":"t1", "name":"web_search", "arguments":{ "query":"…" } }
tool_result
工具结果回填，与 tool_call 同 id 关联，带耗时。
{ "type":"tool_result", "id":"t1", "content":"…", "elapsed_ms":1240 }
artifact
可预览产物（HTML/文件/图表），前端开预览面板而非塞进正文。
{ "type":"artifact", "id":"a1", "kind":"html", "title":"报告", "url":"…" }
stage
阶段切换（thinking / tool / answer），驱动顶部指示条。
{ "type":"stage", "value":"tool" }
为什么 reasoning 要单独成一个事件？推理模型（R1/o-series）会把"思考"和"回答"拆成两个字段返回，且可能根本不返回（agnes 这类非推理模型）。把它独立成事件，前端才能决定"是否显示思考块"，而不会把推理文本混进正文。我们后端 adapter 已能解析 reasoning_content，只差让模型真的返回。
tool_call / tool_result 为什么要用 id 关联，而不是一条消息？
因为工具调用和结果是异步、可多并发的：一次回复可能并行调 3 个工具，每个先后返回。用 id 关联，前端才能把"哪个结果回填到哪张卡片"，并在结果到达前让卡片显示 spinner。若合成一条消息，就无法表达"调用中 / 已完成"的中间态，也无法并发。
4

前端规范：事件 → 组件映射 + 阶段状态机渲染规则

前端维护一个事件→组件的映射表，和一个阶段状态机。收到事件就 dispatch 到对应组件；stage 事件驱动顶部指示条在 思考中 → 调用工具 → 撰写回答 之间流转。

事件 → 组件

token      → MarkdownStream（流式 + 高亮）
reasoning  → ReasoningBlock（可折叠）
tool_call  → ToolCard（参数 JSON）
tool_result→ ToolCard.result（回填 + 耗时）
artifact   → ArtifactPanel（预览）
stage      → StageIndicator（三态）

阶段状态机

点「播放状态流转」，看 stage 事件如何驱动指示条 ↑
稳定 key 分块（防重播闪烁）：MarkdownStream 把已输出文本按行切分，每行用固定索引做 key；diff 时只渲染新增行，旧行保持不动。这样流式追加像"打字机"，而不是每次整段重新淡入。
ArtifactPanel 和普通回复正文有什么区别？
正文是对话流的一部分（Markdown 文本）；Artifact 是独立、可复用的产物——一段 HTML、一个文件、一张图表。它不应该混在聊天气泡里滚动消失，而应放在侧边预览面板或独立标签页，支持反复查看 / 编辑 / 导出。WorkBuddy 的"artifact"就是此意。MiniClaw 目前完全没有这一层，是后续可补的亮点。

落地到 MiniClaw：现状 vs 要补行动清单

对照上面契约，MiniClaw 目前有什么、还差什么。绿色是已具备，红色是要补的。这部分可直接回填进 docs/SSE-CONTRACT.md 与 docs/ARCHITECTURE.md。

✅ 已具备

  • SSE 基础链路（token / trace / step / ping）
  • reasoning 解析已接（adapter 解析 reasoning_content）
  • 前端 SSE 订阅 + 状态机雏形
  • 工具调用以 trace-step 字符串展示

❌ 还要补

  • 真正的流式 Markdown 渲染器（代码高亮 / 表格 / 列表）

  • Artifact 事件 + ArtifactPanel 预览
  • 稳定 key 分块防流式重播闪烁
  • 换推理模型验证 ReasoningBlock
正式版改动文件（建议）：
· 后端 src/core/adapter/*.ts：把工具调用拆成结构化 tool_call/tool_result 事件
· 后端 src/core/gateway/index.ts + src/office-server/index.ts：emit 并广播上述事件
· 前端 src/office-web/src/pages/ChatPage.tsx：引入 MarkdownStream / ToolCard / ArtifactPanel + 稳定 key 分块
· 文档 docs/SSE-CONTRACT.md：补全 6 种事件形状
先对齐"最终产出"再写代码，有什么好处？
避免像上一轮那样"跑偏"——我们先把事件契约 + 组件映射这层正式架构定下来（本 demo 就是契约的可视化），再写代码，所有前端组件都对着契约实现，后端按契约 emit。这样 Web 版和未来的 Electron 壳共用同一套，且换模型 / 加工具都只是"多一种事件"，不破坏 UI。也方便回填进正式文档，对接长期架构。
